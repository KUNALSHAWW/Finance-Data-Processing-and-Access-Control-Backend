1 Every write is chained

Each audit entry stores the hash of the entry before it and a digest of the row's new state, in the same transaction as the change itself.

2 Someone edits the database

A raw SQL UPDATE skips the API, so no audit entry is written. Hiding a large expense takes one line.

3 Verify points at the row

Recomputing the chain and comparing every live row with its last audited digest names the exact record that no longer matches.

Under the hood

Access control

JWT with BCrypt, account lockout after 5 failures, and roles re-read from the database on every request, so deactivating a user takes effect immediately. Every cell of the role matrix is a test.

Correct money

BigDecimal and DECIMAL(19,2), validated amounts, totals computed by the database with GROUP BY, optimistic locking on edits.

Explainable anomalies

Modified z-score on median and MAD per category. Each flag says why, and a huge outlier can't hide itself the way it does with mean and standard deviation.

Call it yourself

The demo accounts are public. Replace <token> with the token from the login response.


        

        
What it does not do. This is tamper-evidence, not tamper-proofing. Someone who rebuilds the whole chain consistently will pass verification unless the head hash is stored somewhere they can't edit. FAQ

        
Is this real data?
No. It is synthetic and the sample accounts are public on purpose. The data resets itself every 30 minutes, and the Admin can restore it any time from the Tamper Lab.

        
Why did the first load take a while?
The API runs on a free host that sleeps after 15 minutes without traffic. This page wakes it as soon as you arrive (the chip in the header shows progress), which usually takes under a minute.

        
What database does the live demo use?
An in-memory database seeded at every start, running the same Flyway migration as production, because free hosting has no durable database. The project itself targets MySQL 8 and is also run end to end against it with Docker Compose.

        
Can someone with database access beat this?
Yes, if they recompute the entire chain. Publishing the head hash somewhere they can't edit, and revoking UPDATE/DELETE on the audit table from the application's database user, closes that gap.

        
Why median and MAD for anomalies?
A single huge outlier inflates the standard deviation enough to hide itself: with 7 samples its z-score can never exceed 2.27. Median and MAD aren't distorted that way. The cutoff of 3.5 is the one recommended by Iglewicz and Hoaglin.

        
What do you track?
Only the utm_* labels of a tagged link, so the owner can tell which application link was opened. No cookies, no IP addresses, no identifiers. Your theme choice is stored in your browser. You can opt out from the notice at the bottom.
